How Much Image Is Enough?

The Gothenburg Research Infrastructure in Digital Humanities (GRIDH) creates and develops digital resources and publications for researchers and institutions. Many of its projects revolve around image data: paintings, inscriptions, rock art, archival documents etc. Depending on the project and the purpose of the documentation, these images can be extremely large. One example is the documentation of Edvard Munch's monumental painting The Sun (1911), roughly 8 by 4 and a half meters, which has been documented through photogrammetry to produce both a measurable orthophoto and topographical visualisations. The resulting images, processed from 7,980 high-resolution photographs, are in excess of 150,000 pixels wide with file sizes above xx gigabytes.

For viewing, this is a solved problem as each project exposes its images through the IIIF Image API, so a browser only fetches the tiles and resolution it needs for display (IIIF Consortium 2026). However, there are several challenges when it comes to offering end-users the possibility to download the image data. While researchers, students, and the public want a file to put in a slide, annotate, print, cite or compare, the original is often the wrong answer to that request. It may be too large to download over an ordinary connection, too large to open on an ordinary laptop, and too expensive for the infrastructure to serve repeatedly. Withholding it is also the wrong answer if the infrastructure is committed to open data. Hence, we present the design reasoning behind a small on-demand download service that sits between these two answers (Terras 2015; Wilkinson et al. 2016). 

There needs to be a compromise for offering an easy-to-use solution for researchers while not putting too much pressure on the infrastructure in regard to bandwidth and processing time (Star and Ruhleder 1996). For the end-user obtaining a file should require no knowledge of tiles or API parameters, the choice offered should be one they can reason about, the result should open in ordinary software, and the same request should give the same file at a stable, citable address. For the infrastructure, the service should be adaptable to widely different image originals and not make presumptions of what constitutes high or low resolution, never do the same expensive work twice, fetch only from sources the infrastructure controls, keep each project's files in that project's own space, and be nimble enough for a small team to understand and repair. 

The most consequential decision follows from combining the requirements above: resolution is offered as three relative size levels (full, half and quarter linear scale) instead of as one or several fixed sizes. Because pixel count scales with the square of the linear dimension, the half level holds a quarter of the original image’s pixels and the quarter level one sixteenth (6.25 percent). Furthermore, an additional option lets the user limit the downloaded image file to a crop of the current view. Hence, the request to the download service names the project's image API, the image, a size level and a format (JPEG or PNG). The service first checks a lightweight index for that exact derivative and returns the existing file if there is one. Only otherwise does it fetch the source, convert it, store the result in project-scoped public storage and record it. The system recovers when files are moved by hand, and a per-image lock ensures that simultaneous requests for the same derivative trigger only one conversion. If the original image size exceeds a size specified by the individual project, the full-size option instead directs the user to a separate repository page on Zenodo, relieving the local infrastructure of the traffic. The half and quarter size options are then instead calculated from a fixed size of 15,000 pixels (longest side), preventing these options from resulting in excessively large requests.

We argue that this design makes the trade-off between fidelity and cost an explicit, informed choice at both infrastructure and user level. At infrastructure level, an open service can be offered without exposing it to unbounded cost, and reuse of derivatives reflects the position that fidelity should be justified by use, while at the user level informed decisions can be made about how much image is enough (Pendergrass et al. 2019). That is an interpretive judgement which depends on the material and the argument being made, and three named but relative levels, coupled with the option to only download a crop of the current view, make it explicit.

The service is a working prototype, and what we present here is its design rather than a user evaluation. That evaluation is the natural next step: whether three relative levels and a crop match how researchers actually decide how much image is enough is an empirical question, and one we intend to put to the users of GRIDH's projects.
